# How vitant works

StrykerJS starts a new Vitest run for every mutant, so each mutant pays for a worker, the test environment and the import of the test file. This tool tries the mutants inside workers that are already running, many per worker, to learn which test file is likely to fail on each, and then settles every mutant with as few runs in a fresh worker as that allows: one for a mutant a test failed on, one per test file for a mutant nothing failed on.

## Statuses

"Fresh worker" below means a worker process in which nothing of the project has run, or a copy of one.

| Status | Meaning |
|---|---|
| Killed | A test file failed when run whole, in a fresh worker, with the mutant on from before the file was imported: in a test that had failed with the mutant while trying it with the file to itself, or twice with one of the two runs made while nothing else ran. A worker that dies in such a run counts as the file failing, as it does for Vitest. |
| Timeout | The same, with the file running into a loop or a hang instead of failing. Counted as detected. |
| Survived | Every test file the mutant can change anything in passed, in a fresh worker, with the mutant on from before the file was imported. |
| Unconfirmed | Every test file that was run with the mutant passed, and something that reaches it was not run: a test left out of every run for failing with no mutant on, which the report names, or, with `--confirm <n>`, the test files beyond the `n` nearest. Or a file failed with the mutant in a test that reaches it and passed in another run: the mutant has made that test a matter of chance. Or all that failed with the mutant was a test that had failed and passed with another, which is named. Or, with `--led`, a file failed with the mutant next to other runs and no run made with nothing else running was made to confirm it; the report names the file. Counted as survived in the score. |
| Led | Only with `--led`: a test failed with the mutant while trying it in a worker and passed again without it, and no run of a whole file was made to confirm it. The report names the tests. Counted as survived in the score. |
| NoCoverage | No test runs the mutated code. |
| Static | The code only runs while a module loads, and no test or hook reaches it. Not run unless `--static` is given, and then judged like any other. |
| Pending | The run gave up on a test file before the mutant was settled. |

## Finding where each mutant is likely to be detected

1. **Mutant schemata.** Every mutant is compiled into the source once, behind a runtime switch: `__vitant__.a === 12 ? a - b : a + b`. Mutants are found with `oxc-parser` and spliced in as text. The mutators and their names follow StrykerJS.
2. **Mutants run inside the test's own worker.** A custom Vitest runner makes each test repeat, with `beforeEach` and `afterEach` around every repeat, turning on one mutant per repeat. The test file is imported once.
3. **A failure is checked against a run without the mutant.** Re-running a test in one process can fail for reasons unrelated to the mutant: state an earlier run left behind, a flaky test. A test that fails with a mutant is run again without it. If it passes, the mutant has a lead: a test file to run whole. If it fails too, the worker's state is no longer trusted and it is replaced. A test that ran out of the time Vitest gives it is not run again: in a run of rea's `ExecFileOutput.ts` the run without the mutant ran out of it too, five times in five, 30 s each, so the worker is replaced and the mutant's file is run whole, as after such a failure.
4. **Runs that cannot change anything are skipped.** During a test's unmutated run, probes compute what each mutated operator, condition or literal would have produced and follow that value through the enclosing arithmetic, comparisons and calls of built-in `Math` functions, for as long as nothing else could have seen it. If the value never differs where that chain ends, the test cannot fail because of the mutant and is not run with it: `Math.round((value + Number.EPSILON) * m) / m` with `-` for `+` almost never rounds differently. Only primitives are recomputed, so no code of the program runs twice. A mutant that replaces a condition with `true` or `false` also drops the evaluation of that condition, so it is only cleared this way when that evaluation was seen, as it ran, to do nothing else: it did not throw, every property and global it read was plain data rather than a getter or a proxy, every operator got primitives, and nothing in it that can run code was reached, which leaves a call the condition short-circuited past, and calls of built-ins such as `Number.isFinite`, `Array.isArray` and `Math.abs` that are still the original functions.
5. **A coverage round, then a plan.** The first round runs every test once, unmutated, to learn what each one reaches; fast tests try their mutants right away. The main process then gives every remaining mutant first to the one test that reaches the most code, which in measurements found a killer first far more often than the cheapest or narrowest test, and only afterwards lets every test try what is left, each mutant as soon as its own first try is over: waiting until every mutant had made its first try left rea's `ExecFileOutput.ts` five rounds of a few tries each, 27 s to 92 s apiece for a test that sleeps, and taking that wait out made the run 1,004 s to 905 s and immer 85 s to 77 s, every verdict as before.
6. **Work is cut into chunks that any worker can claim.** A test's mutants are split into chunks of about a quarter second, claimed through lock files, so several workers can share one heavy test and a round ends within one chunk of its work running out. Workers skip the tests they do not drive; a file whose tests turn out to depend on earlier ones is replayed in order instead, by each worker only as far as a test that some other worker has not taken.
7. **Loops and hangs do not cost a restart.** Instrumented loops count iterations and throw when a mutant run goes far beyond the unmutated count. A hung `await` is abandoned by a timer that waits longer while the test is still using CPU. A mutant that is only slow is left to Vitest's own test timeout. A watchdog thread is the last resort for a mutant that blocks the event loop for good: it measures CPU time, so that a busy machine does not look like a hang, stops the worker after what a run may take, and leaves the mutant to a fresh worker, which calls it a timeout only after five times that. What a run may take comes from the test's run with no mutant, which came after the tests before it; a worker of a later round skips those, and the test then does first what they had done. In shiki the first test of a file loads every grammar once, and on a 3-core CI runner the first try of the next test in each new worker went over the limit for that alone, with 24 mutants one after another, a round each: 32 rounds for 11 and 500 s for 204 s, with every verdict as before, since the runs of whole files decide. A worker stopped in a test's first try there says nothing of the mutant: the mutant stays as it was, and the file's tests are run from the first in the rounds that follow. A mutant that ends the process outright is found the same way round: every worker leaves word of the mutant it is about to try, and one that is gone with a mutant named has that mutant left to a fresh worker and the rest of its work shared out again.

## Deciding

What a test does with a mutant inside such a worker is not what the suite would do with it. The mutant is on for that test alone, after a file that loaded without it and tests that ran without it, in a process where the test has already run once. Four things were measured to go wrong, each on a real project (ground truth being the mutant put into the source and the plain suite run):

- **Code that also runs while the test file loads.** immer's tests compute results in `describe` bodies and the tests only compare them; a mutant that is on during the test alone changes nothing they look at.
- **Code that only acts the first time it runs in a process.** immer's plugin registry keeps the first implementation it is given. In a worker where the unmutated run came first, the mutated one is built and dropped.
- **What an earlier mutant left behind.** In es-toolkit, `arr.sort()` for `arr.slice().sort()` returns the same result, so the mutant passes, but it sorts the array a `describe` block shares; every later mutant of the sort then passes on data that is already in order.
- **A failure that only the half-way state produces.** pinia installs its devtools plugin under a condition. With a mutant making that `true` for one test of `ssr.spec.ts`, the test fails, passes again without the mutant, and fails again with it; with the mutant in the source from the start, the file and the whole suite pass.

Nothing the instrumented code can observe tells these apart from an ordinary pass or an ordinary failure. So no verdict comes from inside such a worker:

8. **Every mutant is settled by running test files whole.** A fresh worker runs the file once, as a plain run would, with the mutant on from before the file is imported. A mutant that a test failed on gets the file of that test. If the file fails in that same test, the mutant is killed. A failure in another test settles nothing by itself, so the run does not stop at it while the test that gave the lead is still to come: it goes on as a plain run does, which does not stop at a failure either, and that test failing too settles it. That holds past a test that ran out of the time Vitest gives it, as a plain run goes on past that too; a loop this runner ended, which a plain run would never have got past, and a second test that ran out of its time end the run. Where one jotai test waited out its five seconds with a mutant and the run ended there, the test that gave the lead was never reached, and fifty mutants each took three more runs of five seconds, one of them made with nothing else running: run with that file alone, 669 s, and 193 s going on to the test that gave the lead, every verdict as before. Where it does not come to that, other evidence is looked for, in rounds of their own once nothing else is left to do: the tests that failed try the mutant, each file with one worker to itself, and so does a test whose lead was made next to other runs of its file; a test that fails with the mutant and passes without it makes the failure already seen count. A test that cannot be run a second time in a worker, because it fails any second run whatever is on, has no such try to make: it gets its one run in a copy of a worker that went through the tests before it with no mutant on, the mutant coming on as the test begins. One such copy is made with no mutant at all and has to pass, and up to three with mutants the file is known to pass with, which the test is to pass with as well: a test that fails by chance meets those as a matter of course while it tries mutants in a worker, and here it would otherwise only ever be given mutants its file failed with. For a file that timed out without naming a test, where the mutant was reached while loading, up to four other tests may be asked for a witness before that last confirmation. Each comes from a different file with pristine coverage that did not reach the site while loading, with broader coverage first and a stable tie-break. A request spends its place even if the worker leaves no result; the bound is a count, never elapsed time. A new lead still needs the existing whole-file confirmation, and a failed or exhausted search returns to the complete confirmation path. What is still open after that gets a run of the file while nothing else runs, one file a mutant, the cheapest first. Nor does a lead vouch for a failure of its own test once another lead of that test came to nothing, its file passing with the mutant (a lead whose test failed again without the mutant does not count: that says how the mutant left the worker, and in rea it took 40 of 46 such tests out of settling anything, sending 220 failures to runs made one at a time that all confirmed them; on solid, where the runs it spares wait out a witness that ran out of its time either way, it changed nothing): a test that fails by chance on a busy machine fails with whatever mutant it is trying, and on a 4-core CI runner one such test of hono, which every mutant of the router reaches, failed once while trying a mutant and once more in the run of the file about once a run. A lead from one test does not vouch for the failure of another: a mutant switched on in the middle of a worker's life can fail a test that the file run whole does not, and with such a lead any other test of the file failing twice on a busy machine would settle it. If the file passes, the lead was wrong and the mutant goes on like any other. A mutant with no lead is run with each test file in which it can change a value, while the file loads, in a test, or in a hook (`beforeAll`, `afterAll`, those that clean up after a test, the teardown of a fixture), a few files first and then the rest: the files whose tests go through most of the mutant's source file while they run, then the cheapest; a failure there ends the search, and counts once it is settled as above. That holds within a round too: the mutant's other files are not begun in the round in which one failed, and are as open as before if the failure comes to nothing. In Effect two mutants had gone on through 240 more test files after one had failed, and runs begun after their mutant had failed a file were 8 in a hundred of the time spent on runs of whole files on Linux and 13 on macOS. Which file is cheap says nothing of which one fails: of the 322 test files that load Effect's `Chunk`, one to three fail on most of its mutants, at the median the 181st cheapest, and with the cheapest first 120 mutants that were detected in the end passed 35,500 runs on the way, four fifths of all the time spent on runs of whole files. The file whose tests reach most of `Chunk` is one that fails for 109 of 113 such mutants. Only a mutant that passed every one of its files is reported as survived. Which files those are is read from what each test reached in its run without a mutant, and that run has to be one a plain run could have made: in a worker no mutant had been tried in, and with no test before it that failed there or ran out of time under the probes. A mutant that a test let through can leave the module as no plain run has it, and the tests after it then go another way. In vue such a mutant left an effect active; the one test that fails on `else if (true)` for `else if (__DEV__ && !failSilently)` returned before that line with no mutant on, so its file was not among those the mutant had to pass, and the mutant was reported as survived without ever having been run with it. Files with a test measured in such a worker get a pass with no mutant tried, in which every test has its run; rounds that give only some tests a run, the failed ones their second or those a lost worker left out, used to count as that pass and no longer do. The pass is one worker's, which tries nothing, in the round of the file's tries: made once nothing else was left, it was a round of its own, 33 s of rea's `ExecFileOutput.ts`. What it reaches adds to what the test's other unmutated runs reached rather than replacing it: in rea a test that races a timer missed a branch in a pass made beside twelve other runs, and a mutant there had no file left to pass. A test that fails with no mutant on is left out of that pass, as it is left out of the runs of the whole file, so that the tests after it are seen as those runs will have them: 27 tests of hono's `streaming.test.tsx` fail under this tool every time, and a test of vue that checks how long a chain of computed values takes fails under the probes more often than not. There are two such passes, and one more whenever a test has since been found to fail. A file that still has a test without such a run is run with every mutant that is left, and the report names it; none of the fifteen scopes checked ends with one. In these runs a loop is not stopped for being long. The count of iterations that ends a loop while tests try mutants only says the loop is longer than it was: a mutant can send it over three million elements that it is through with in milliseconds, and the suite passes. Past its count, a loop goes on until it has also kept the process busy without a pause for a second or twice what the file takes, and never for less than the finite time Vitest gives the test or the particular hook invocation: a loop that is through in four seconds where a test has a minute passes the suite. For a timed hook, its own effective timeout and expiry check are observed inside Vitest's wrapper, after that wrapper has installed its deadline. The invocation keeps its clock and processor start across asynchronous work until Vitest settles it; a completed hook's later callbacks do not keep its deadline. Shared supervisors retain the largest hook allowance seen in that whole-file run, so a shorter parallel hook cannot stop the longer one. A hook that catches the loop interruption is still judged by Vitest's own expired deadline. The wrapper is observed only where its deadline and settlement structure can be verified; a worker that did not load that observer fails explicitly. That time is by the clock as well as on the processor, as Vitest's is by the clock: the processor time of a worker counts the garbage collector's threads, and a loop that kept the objects it made for a while used six seconds of it in four by the clock. The watchdog lets such a stretch go a second longer than that, so that the loop ends in its test, which a lead of the same test vouches for; a stretch the watchdog ends on time on the processor or on memory names its test as well, one it ends by the clock does not. A run that waits without using the processor at all, on something a mutant keeps from happening where Vitest gives no limit, as while the file loads, is ended by the clock. The clock counts from the last point where the run was seen to move on, a suite or a test starting or ending, and stands still while the body of a test with a limit of Vitest's runs and the event loop turns, so that Vitest's timer can end it: on the run as a whole it called a file a timeout whose thirty tests each waited a second under a limit of five ([limits](limits.md)). A worker that is gone without a word counts as a failure once it has happened twice. Two failures in a row are made within milliseconds of each other, and on a machine that is busy at that moment both can be the machine's: on a 4-core CI runner a test of hono that sleeps a second and checks the time it logged failed twice for a mutant in a router it has nothing to do with, which was the wrong verdict there from the start. So where no test of the file ever failed with the mutant while trying it, the failures being all there is, one of them has to be made in a round of its own, with nothing else of its file running, and with `--strict` with nothing else running at all, one run at a time on the machine. By default the files of that round go side by side, one run of each at a time, but for those whose runs have got in each other's way, which wait for the machine to themselves: on formbricks the round took 65.3 s against 125.2 s, and the run 351.8 and 357.6 s against 401.1 to 444.4 s, every verdict sampled agreeing with the suite. What that gives up is the machine to itself: a test that fails on a busy machine can fail beside other files there as it did in the first run, and two test files that bind one port or write one path and never meet in the suite can fail each other ([Limits](limits.md)). That takes for granted that the file passes there with no mutant on, which the first round, where everything runs side by side, does not show. In h3 a test that sends a server on a port a body too large times out six times in six when its file is run alone and passes as a rule with the whole suite around it; sixteen mutants it has nothing to do with were reported as timeouts, with copies off, and with them on the same mutants survived. So the round has runs with no mutant among its runs, as alone as they are: two initial controls, one after every six planned mutants and one at the end of the plan. A worker started for a mutant claims that job before copied controls, so the plan does not guarantee that the controls execute first. A test that fails in any of them fails by itself and is left out like one that fails now and then, for what it had been taken to show before as well, and the round is planned again from there; a file that fails that way with no test to name is given up on. Where a copy of a file ended without a verdict, one more is made with no mutant on, and a file such copies fail twice or do not get through is run in started workers from then on: on macOS the system ends a copy that touches what a native module set up in another thread, hundreds of times over in vite, and each is a run to make again. That saves runs and proves nothing about the copies that pass. A test that fails a file's run with a mutant and passes the next run of the same file with the same mutant fails for reasons of its own, a wait on the clock on a busy machine for one; what such a test fails is not counted, as a verdict or as a lead, and the report names it. A run that such a test ended never reached the tests after it, so its mutant is run again without that test rather than reported as survived. The report is made from these runs alone: what a test found is nowhere in it, and a lead whose record was lost with its worker is tried again rather than taken on trust.
9. **Which files those are is measured with no mutant tried.** The unmutated runs of the first round can come after mutants were tried in the same worker and may have seen what one left behind. Before the whole-file runs are planned, such files are gone through once more, untouched.

A suite hook can depend on an earlier test too. If a worker skips that test, the hook can fail before any planned test begins, leaving no test record to request a replay. A file whose own or nested suite's hook fails in such a run is replayed from the start. The suite's aggregated failed state is not enough: it also includes tests that failed while trying mutants. Failures in runs of whole files still count as failures. `fixtures/basic/test/hook-order.test.ts` exercises both cases with the initial round's trials disabled; i18next's `hasLoadedNamespace` tests exposed the missing replay by leaving their planned tests unrun.

The unmutated runs inside such workers also decide which tests are left out of every run for failing by themselves, the whole-file runs included, so the repeats themselves must not change what a test meets. One way they did is through the project's mocks. Before Vitest 5 every mock is kept in one registry, and those made before a try ended are held only weakly so that thousands of repeats do not fill the heap (item 15). `vi.clearAllMocks()`, `resetAllMocks()` and `restoreAllMocks()` go through that registry with `forEach` up to Vitest 3.0.6 and by spreading it from 3.0.7, restoring in reverse; the tool had only reached the first way. From the second test of a worker on, a mock the test file made while it loaded was never cleared, call counts grew from test to test, and a test that counts calls failed with no mutant on: in Roo-Code (Vitest 3.2.4) 25 tests of `qdrant-client.spec.ts` were left out and 207 mutants of its source reported as covered by no test, and on the fixture below five mutants the suite detects were. Both ways go through the mocks held weakly as well, first, in the order they were made, as the plain suite has them. `fixtures/mocks` runs on Vitest 3.2 for this, from the root's `vitest3`: on Vitest 5 the registry is not a Set and nothing is held weakly.

A run of a whole file has to end where the suite's run of it ends, too. Vitest 3.2 tears a fixture scoped to the worker (`test.extend` with `scope: 'worker'`) down once the file is through, after the point where a copy ends and where a worker started for the run has said its verdict, and fails the run when the teardown throws: an assertion there on what the tests left in the fixture fails the suite with every test passing. Both mutants of the fixture project's `fixtures/mocks/src/box.ts` were reported as survived that way. A run of a whole file runs those teardowns itself, with the mutant still on, once each, and counts one that throws as the file failing. From Vitest 4 such a teardown failing fails nothing (checked on 4.1.10 and 5.0.3), and there it is left as it was.

The environment the tests meet must be the suite's as well. Vitest's CLI sets `TEST`, `VITEST` and, unless set, `NODE_ENV=test` before it creates the instance; the tool creates the instance itself and had set none of them. In actual (loot-core) `sheet.ts` skips a cache database only under `NODE_ENV=test`, so all eight tests of `base.test.ts` failed with no mutant on and none of the 298 mutants of `base.ts` was detected, while the suite detects `getBudgetType() {}`; formbricks failed about 150 tests on its environment schema, and in Roo-Code a module watched files outside any test and the file never settled. The tool now sets the three as the CLI does. `watch.test.ts` in `fixtures/basic` passes only under `NODE_ENV=test`, and the end-to-end tests run the tool with the three variables taken out of the environment, since Vitest sets them for the test that runs the tool and the child would inherit them.

The code the tests meet must also be the code this run put the mutants into. Vitest can keep the modules it has transformed on disk, in `node_modules/.vitest-cache` at the root of the workspace, and hand them to later runs: from 5.0.4 it does by default, and 5.0.3 and 4.1 (`experimental.fsModuleCache`) do when the project turns it on. The key is the module's id, its source as it is on disk and the environment: the config, the names of the plugins, `NODE_ENV`. What the tool's `load` returns is not part of it, so a run was served whatever the last run on the project had made of a file: the plain code where that run did not mutate it, or switches with that run's numbers for sites and mutants, which here answer other mutants and mark other sites. In immich (Vitest 5.0.4) a run of `utils` had left every service plain and the utilities with numbers of their own; the next run of `services` reported all 709 mutants of `person.service.ts` as covered by no test, and so every mutant of the files after `memory.service.ts`, while the kills and the coverage it reported in the files before those came from the utilities' switches answering mutants of the services. The tool turns the cache off for the root and for every project declared in it. Nothing is lost by that, since within a run Vitest's module graph in memory still transforms each file once: on immich a run of `person.service.ts` took 111.8 s with nothing cached and 123.9 s served from the cache. The end-to-end tests run a copy of `fixtures/basic` with the cache turned on, mutating `math.ts` and `words.ts` and then `words.ts` alone, which must give what a run with nothing cached gives; served the first run's switches, every mutant of `words.ts` came out as covered by no test.

A mutant in code that runs while a module loads can change a value in every file that loads the module, and so far as what ran tells, it has to pass them all. For a value the module only makes and hands out, that is far more than can matter. In umami, 749 of the 1,293 mutants that survive are strings and lists in `src/lib/constants.ts`, `export const AUTH_TOKEN = 'umami.auth'` for one; every one of them was run with the 59 test files that load the module, 45,783 runs of 48,028, while StrykerJS, which runs only the tests that reach a mutant, took a tenth of the time. Such a value can change nothing in a run until something reads the binding that holds it, so a file whose run reads none of the bindings it flows into is not run with the mutant:

- The binding is a top-level `const` whose initializer runs no code of the program, cannot throw and does nothing but make its value: literals, objects and arrays of such values, operators on values that are primitive by their syntax (no BigInt, which a mutant can put under an operator that throws on it, `+1n` for `-1n`), `process.env`, functions, earlier bindings of the kind, a key one of them has as its own in an object literal with no accessors (`[ROLES.admin]`), a call of a function of the module that only returns an expression of its parameters (`f('id')` for `function f(type, opts) { return { type, ...opts } }`, checked with the arguments in their place), and a `Set`, a `Map` or a frozen object of such values. The last three run no code of the program only while `Set`, `Map`, `Object.freeze` and what they call on an array are the built-ins, and, for the key, while `Object.prototype` has nothing added, where a mutant that empties the object sends the read; so no key `Object.prototype` has is taken, and the module checks the rest as it comes to the declaration, and where they do not hold, counts the binding as read there. The bindings it flows into are itself and those of the kind whose initializers read it.
- A read is marked by a plugin that sees every module Vitest serves but dependencies and style sheets, after the other plugins: at the start of the function the read is in, at the start of the module where it is in none, and in place where it is in a default value of a parameter, which a function declared at the top of a module can evaluate through an import cycle before the module's own code has run. A module is followed by the names it is imported by, the default included, through a namespace, `const x = await import(...)`, which is what Vitest makes of the imports of a file that mocks a module, `const { a } = await import(...)`, and through the modules that pass the names on (`export { a } from`, `export *`, an imported name exported again), read from their sources on disk: Vite makes a re-export a getter, so passing a name on reads nothing, and a module that does is not taken to read what it passes on where its importers can be followed to it. A chain of re-exports that comes back to a module on it makes every name of that module stand for every binding. Every other way to reach it counts as reading all of it, at the start of the module where it may come first: a name passed on that is not followed, a namespace used other than for a property, `vi.mock` and the like given its path (a factory can spread the original), a module loaded by a path that is not written out, `import.meta.glob`, `eval`, and a module that does not parse.
- Where a file reads the bindings a mutant changes in its tests or hooks alone, never while it loads, its run is a copy made after the file loaded, with the mutant off while it did: the copy turns the mutant on and makes those bindings again, in the order they are declared, before the first test. Nothing read them until then, so the process differs from one that loaded with the mutant on only in what they hold, and their initializers, made again, hold what the mutant makes of them, as long as what they are made from is as it was: the bindings made again before them, and others that are primitives, since an object a test or the module changed after it loaded would give another value; a binding made from `process.env`, one the module assigns and one declared with others are never made again. The `const` becomes a `let` of the same length, and every copy of the module, as `vi.resetModules` can load two, makes its own again; a copy that finds a read of one of them while the file loaded leaves the run to one made before it. On actual a run that passes takes 0.4 s in a copy made after the file loaded, at the median, and 2 s in one made before. A third agent set on this found an object a binding was made from changed after the module loaded, and a module loaded twice; both are closed and in `test/reads.test.ts`.
- A file is taken to read a binding where any unmutated run of it reached the mark: while it loads, in a test or in a hook. Where no file does, the mutant is run with one file that loads the module all the same: that the initializer can neither throw nor do anything else is the instrumenter's reading of it, and a run that loads it shows where that reading is wrong. A file reused with `--incremental` counts as having read every such binding, since what it read is not kept.

This rests on the same assumption as every run left out for a probe: a test does what it did in its unmutated run until it meets a difference, and with the mutant only in the values of these bindings, the first difference is a read of one. Before it was kept, an agent asked to break it found five ways to a wrong survivor, each with a project of its own that the suite and the tool disagreed on, and all are closed: a default import of `export { x as default }`, `+1n`, `vi.importActual` given a variable, a virtual module the plugin skipped, and a default value of a parameter read through an import cycle. A second such agent, set on the barrels, the functions called in an initializer and the reads of a key, found eight more: `new Map([])`, which a mutant makes `new Map(["Stryker was here"])`; a function's parameters taken for those of the function it calls, and an argument read as the parameter of the same name, once in a loop that never ended; a parameter of the same name as a binding, which the mark was put around; two `const mod = await import()` in one file taken for one; a barrel read once for two projects that resolve its import to two files; a function given another value by a `for...of`; and `Array.prototype` given an index, or `Object.prototype` a key before the runtime was made. All are closed, the projects agree with the suite but for an import by a path in another case, which goes past every mutant and is a limit of its own ([Limits](limits.md)), and `test/reads.test.ts` holds every case but the virtual module and the two projects. `fixtures/basic`'s `labels.ts` has a constant for each way of reading one, a test that sees a `Set` only through a `Set.prototype.add` of its own, and one that nobody reads. On umami it took the whole-file runs from 48,028 to 14,856, every verdict as before and all 1,367 checked against the suite agreeing. What is left is mostly files that read such a binding while they load: 11,208 runs of `constants.ts` mutants.

This costs one run of a test file per detected mutant, cut short at the failure, and one per file for every other mutant. That cannot be shared between mutants without giving up what makes it right: a process that has seen nothing else.

## Making such a process cheap

Started the usual way, such a process costs more than the tests it runs: Node, Vitest's worker and the test environment come to about 0.1 s of CPU time before a test file is even imported, and to 0.45 s with jsdom, where the tests of a file often take a hundredth of that. So the process is not started. It is copied:

10. **A worker that has started up is copied with `fork()`.** A worker that has loaded Vitest and the environment and has run nothing of the project is, for every mutant, what a new worker would be at that point. For each whole-file run it makes a copy of itself, which turns the mutant on, runs the file and ends; the worker waits for it and makes the next. Node has no call for this (`child_process.fork` starts a new process), so a small addon in Rust (`native/src/lib.rs`) calls `fork()` and `uv_loop_fork()`, which gives the copy an event loop of its own.
11. **Once the test file has loaded, for mutants whose code did not run while it did.** A run that had such a mutant on from the start would be, up to the end of loading, the same as one without it. The worker loads the file with no mutant on, checks for each mutant, in its own record of what ran, that the mutant's code did not, and copies itself from there, so the copy pays for neither the start nor the imports. The worker looks at that record again right before each copy, after the call to the main process it waits on: what that wait let run may have reached the mutant's code since (Astra found the gap in a harness of the runner's own methods). Which mutants run while a file loads is learnt from the first round, where each file's worker says so as soon as the file has loaded and not only at the file's end: a worker replaced before then, for its memory, had left four files of immich with no such record, and every run of their mutants went to a copy made before loading, 466 loads of a file and a ninth of the run. Mutants whose code does run while the file loads get copies made before loading or, as below, while it loads, and so does every mutant of a file that leaves something open while it loads: a file descriptor, a socket or a child process. Copies made afterwards would share it. A timer set while the file loads would be due sooner in each later copy, and would go off in the worker while it waits between copies: as the file finishes loading, before anything is awaited, every such timer is put off with what was left of it, and each copy, then the worker, sets it due that long from then. The clocks the project reads stand still the same way: where workers copy themselves, `Date`, `performance.now`, `process.hrtime` and `process.uptime` are replaced before any of the project's code runs, as fake timers replace them, by ones that leave out how long the process and those it was copied from stood still for copies. A file that notes the time as it loads and checks in its second test that a second and a half has not passed, the first waiting 300 ms, had its second test fail in 22 of 44 runs of whole files with one worker, read as failing now and then and with 12 runs made again with nothing else running; with the clocks standing still it failed in none, in 17 runs, every verdict the same (`fixtures/clock`). On immich, where every service test file sets one through `exiftool-vendored`, 6,796 of the 6,888 runs of `services` are then copies made after loading, where none were. Every worker the round gives such a file loads it to be copied from while a run asked for by name is left, whichever worker has taken that run; one that finds every run taken goes on to the tries planned for the file, from where a worker that tries would be, no mutant having been on. Ending there left those tries to a round of their own: going on, rea's `ExecFileOutput.ts` took 426 s against 441 s with `--led --confirm 4`, and immer 89.6 to 98.3 s in three runs against 98.5 to 110.2 s in six, with as many tries, two a mutant at the median, and every verdict as before. Made next to the runs, a try costs more processor time, on immer 0.12 to 0.13 ms against 0.08 ms in a round of its own, 37 to 39 s of it in all against 29 to 32 s. A worker keeps which tests it has found with every share of their tries taken: looked up on disk for each test it passed, a worker that starts after the others came to 25 million lookups and 248 s of twelve workers in one round of immer, more than the round the tries had waited for.
12. **A copy has only the thread that made it.** The workers run V8 with `--single-threaded`, so that nothing is left to compiler or garbage collector threads a copy would wait for in vain, and the watchdog thread of item 7 is not started in a worker that copies itself: it applies the same rule to its copies from outside, reading their CPU time. Copies share the worker's channel to the main process, so one is made only when no call of the worker is unanswered and nothing is half written, a copy reports neither its tests nor what they print to Vitest, and it reads its verdict and ends only when none of its own calls is unanswered. A copy is given the process id Node read in the worker, so it is told its own.
13. **Anything unexpected falls back to a worker of its own.** A copy that ends without a verdict, one that sits for three seconds using no CPU time and never returning to its event loop, as one waiting for a thread it does not have would, and one that goes on past the longest a run of the file may take are stopped, and that run is made by a worker started for it. So is a run for which no copy could be made. So is every run of a mutant that has blocked a worker before, where every run of a file takes a worker started for it anyway (Vitest 3, and Vitest 4 before 4.1.9 where its pool could not be mended): a copy that blocks holds up the copies behind it. Where workers hand their files to copies, such a run is made in a copy, with a worker run of its own so that it holds up nothing. A copy notes the test it is in, in a file the process that copied it reads once it has stopped the copy on its time on the processor or its memory, so that the stop names its test, as the watchdog of a worker started for the run does: without that, 32 of es-toolkit `array`'s 54 such runs waited for a run made with nothing else running. On macOS runners, against the version before in one job, three runs each, `array` took 1.37 and 1.04 times as long before as after, query 1.17 and 1.13, ufo 1.10 and 1.02, every verdict as before. A copy that a worker hands a whole test file to (item 14) is watched less closely, since it waits for copies of its own: it is stopped when for 30 s it has no child, uses no CPU time to speak of, and no event loop of it or of its copies turns, and the file then gets workers started for it. A copy of pinia sat that way for a night, waiting in V8's garbage collector on a lock one of the worker's other threads had held when the copy was made. Where there is no `fork()` (Windows) or the addon is not built, every run is made that way.
14. **A worker is started once and copied for every test file.** Starting a worker, which is Node, Vitest and the test environment, takes 0.35 s of CPU time in valibot and 0.45 s with jsdom in zustand, and a test file was given a new one in every round: 790 of them for valibot's 121 test files, three fifths of everything four workers had to give. In the rounds whose workers copy themselves, Vitest is told not to isolate the files and hands a worker one after another; the worker imports nothing of them. For each it makes a copy of itself, and the copy is the file's worker from there on, setup files included, while the worker waits for it and then tells Vitest the file had no tests. So the worker stays what it was before its first file. The one thing Vitest changes in it after that file, before version 5, is `process.exit`, which it guards against a test calling it only during the first; each copy is given the guard back. With four workers valibot went from 131 s to 69 s and zustand from 32 s to 26 s, every verdict the same. A file with a run to make in a worker started for it is left out and gets its workers as before, in a second pass of the round: that run is made where a copy did not get through, and a copy of the worker is a copy. From Vitest 4.1.9 that pass is a call of its own after the one for the copies: the pool passes the workers that hand their files over from file to file and starts every other for its file, and it takes that setting once a call for a project. Before 4.1.9 the pool starts a worker for every file all the same, since it hands a worker that has ended to the next file and waits for it for good, and both go in one call with those files first: their runs are where a copy did not get through or a mutant blocked or looped, the long ones, and in a call of their own they waited for the copies to be through. On a machine busy with other work, run in turn with the two calls, ufo (Vitest 4.1.5) took 10.1 to 12.2 s where it had taken 12.6 to 13.8 s, three runs each, and its second round 7.4 to 9.3 s where it had taken 10.0 to 10.6 s; valibot (4.1.8) took 48.0 and 51.1 s against 51.1 and 53.1 s. Every verdict was the same. On macOS a copy that is the first to touch certain system frameworks was ended by the Objective-C runtime, before the workers were started with that check off, which is what a file of h3 that fetches did to every copy; with its runs handed to copies as well, none of them ended and the file was given up on with 1368 mutants pending. The same goes for a pass through the file with no mutant on, so a worker that finds its copy ended over nothing a mutant did says so, and the file gets workers started for it from then on. Before Vitest 4 the pool is told once, for all rounds, whether every file gets a new worker, so there it does: with the files of xstate (Vitest 3.2) handed to copies from the first round on, a four-core runner took 417 s where it had taken 264 s.

A mutant whose code does run while the file loads need not have its copy made before loading either. Each module with mutants begins its own code with a call, after its imports have loaded, and a worker with such runs to make loads the file with no mutant on and copies itself there, for the runs of that module's mutants. What ran before is what a run with the mutant on would have run, since no code of the module had, and what was queued to run next stays queued in the copy. So the copy is made on the spot: a pause there, as `standStill` makes, lets what earlier modules queued run ahead of the module's code, and a copy then passed a test that every run of the suite fails where a dependency set a flag at the end of a chain of promises. Not where a site of the module has run already, as a function of it called through an import cycle does before the module begins, which left a value made with the mutant off; not where a call to the main process is unanswered, or anything is open or under way that was not before loading. A timer set while the file loaded is the exception: each copy, and the worker once it has made them, puts it off by as long as the copies took, so that it is due as far into what runs next as it was. A file where no copy could be made has its runs made before loading from the next round. So do runs whose module did not begin while a file loaded that leaves something open; elsewhere they go to a copy made after loading. On umami a test file spends 970 ms of its 1,370 ms of loading on the libraries before `constants.ts` begins, and the scope went from 350 s to 193 s; immich `services`, where `exiftool-vendored` sets a repeating timer while loading and every run had been made before loading, from 1,855 s to 728 s. Every verdict was the same. On a Linux runner that scope made none: `detect-libc`, which `sharp` and `node-gyp-build-optional-packages` call as they load, reads a file and closes it with `fs.close`, a request to Node's thread pool, and nothing lets the event loop turn and see it done before the next module begins. A copy can lose such a request, so none is made there. A run copied while loading but whose module did not begin goes to a copy made after loading only where an unmutated run has said what runs while the file loads: before that, in formbricks' `validate.test.ts`, such copies failed a test beside other runs that the suite passes.

A copy can also be made later than that, after the tests that come before the first one whose run with no mutant reached the mutant's code: those tests go the same way with the mutant on, and a run of the file that starts from there saves them. A worker with such runs to make, once it has made the copies from the end of loading, runs the file's tests on with no mutant on and copies itself in Vitest's `onBeforeRunTask` of each such test, before its `beforeEach`, for the runs whose mutant's code its own record shows has not run in this process. Which test that is comes from the sites each test reached, not from the mutants it could have changed: a test that went past a condition `true` already holds reached the mutant `true` there too, and a copy before a later test would find it ran. The copy is made on the spot, with nothing awaited: a pause lets a chain of promises an earlier test left behind run ahead of the test, where the suite has it run later, and the test then meets state no run of the suite has. No copy is made where an earlier test failed, where the tests run at once (`concurrent`), where a call to the main process is unanswered, a descriptor is open or a resource held that was not before loading, or where a test has changed the file system: a file one test leaves for the next to take would be there for the first copy and gone for the second, and in `fixtures/walk`, with that check taken out, `n / 2` for `n * 2` was reported as survived where the suite fails it. Changes to the file system are counted at the calls of `fs` that make them, outside this tool's session, since a file written and closed leaves nothing open to see. A close under way is let through: it finishes in the worker and never in the copy, which keeps the descriptor, and Vitest leaves one under way in every file of immer that has snapshots, for the whole file. The timers set by the tests before are put off and the clocks stand still as for the copies made once the file has loaded. On immer 665 runs were made that way, and the time of the runs of whole files went from 407 s to 364 s, every verdict as before. Opening the lock that serialises the copies before the file loads, where it had been opened at the first copy and so taken for a descriptor the file had opened, took the copies immer made while files loaded from 220 to 1,529 and those made before from 1,490 to 408.

A copy shares the worker's channel to the main process, and the worker goes on using it. A copy that ends itself because a mutant left it unfit for the tests that follow, or because it holds too much memory, did so on the spot, as a worker Vitest started does, whose channel ends with it. Here that could be in the middle of a message, what a test printed for one: the main process waited for the other half, read nothing the worker sent after it, and the run did not end, three runs of jotai in four on a macOS runner with three cores. Such a copy now waits until nothing of it is on the way and ends with a code that says so, and the worker gives the file to its next copy there and then, being what a worker is before its first file: where a worker Vitest started leaves the rest of the file to the next round, one file of vue taking eighteen rounds for it, the copies follow one another within the round. A copy that ended any other way may have left half a message, so the worker ends itself too, the channel goes with it, and the next round finds the file's work not done. Before, a copy ending itself counted as one that did not get through, and the file was never handed to a copy again: 56 of vue's 89 test files in the `reactivity` scope. That scope went from 1780 workers started after the first round to 1006 and from 143 s to 110 s on twelve cores, every verdict the same. A copy the watchdog stops in a test's first try, before any mutant was on, does not count as one of those either: a worker started for the file would be stopped there as well. Counted as one, it sent immich `utils` to started workers for good, and each worker's stop for its memory took a round of its own, 36 rounds where a run without that took 12 (3,352 s and 3,430 s against 2,699 s on a macOS runner); in the nine runs of that scope since, the rounds were 12 to 19, but for one that a file left to one run at a time took to 55.

A suppressed console RPC still returns a fulfilled promise, as the real RPC does. Vitest 5.1 attaches `.catch()` to that return value; returning nothing raised an uncaught exception after a test had passed. Two mutants of i18next's `PluralResolver` whose only observed effect in the suite was an error log were consequently reported as killed in copies and passed the plain suite. `fixtures/basic/src/logging.ts` reproduces the harmless output, and an end-to-end run resolves Vitest 5.1 through the root's `vitest51` alias. The main suite stays on its pinned Vitest: its script invokes that package's CLI directly, since the aliased versions export the same binary name. Genuine unhandled errors still fail a whole-file run.

Unhandled errors are observed through Vitest's existing worker RPC, after its own listeners and the project's handlers decide whether to report them. The runner leaves those listeners and their identities intact. Replacing them while starting a whole-file run invoked Next.js's patched `process.off`, which warned through an unavailable async context and threw before Formbricks's control ran; some rounds ended without recording the failed control and eventually left mutants Pending. Capturing the native listener methods was insufficient: Next exposes a virtual listener list, and mixing it with native registration delivered an error twice; replacing the actual filter prevented the application from removing it later. `fixtures/basic/test/process-listeners.test.ts` preserves handler identity and delivery while making that internal removal fail. The root `dangerouslyIgnoreUnhandledErrors` setting is carried in the session because Vitest does not serialize this main-process option to workers. Source-written tests cover rejected promises and uncaught exceptions with that setting both on and off, in copies and started workers.

macOS makes copies of a process one at a time: sixteen workers copying themselves at once took 54 ms a copy where one alone takes 3 ms, most of it spent waiting inside the kernel. The addon takes a file lock around the call.

macOS also ends a copy in which a class of its own frameworks is set up for the first time, in case another thread was doing that when the copy was made. The first look-up of a host's name in a process is such a moment: every copy of h3's `proxy.test.ts` ended that way, 138 in a run of `utils`, and after two unmutated copies had gone the same way its other 431 runs were made in workers started for them. Workers are started with `OBJC_DISABLE_INITIALIZE_FORK_SAFETY=YES`, which turns the check off: no copy was lost in the next run and 95 runs in place of 526 took a worker of their own. The fixture project has a test that reads the certificate authorities the system trusts, which ends every copy the same way with the check on, and the end-to-end run fails on the message macOS writes then. What the check guards against is a thread of the worker being at such a class at the moment the copy is made, which leaves the copy waiting for it for good. A copy is made of a worker that has run nothing of the project, or of one that holds nothing open and has nothing under way, so no thread of it is in a look-up then; a copy whose own thread waits that way is stopped as one that is stuck and its run made by a worker started for it. Other locks a thread can hold while a process is copied carry the same risk with or without the check.

On Linux V8 marks the memory it allocates, the JavaScript heap included, as not to be given to a child process (`MADV_DONTFORK`), and a copy made without more ado dies on its first instruction. The addon takes the mark off every mapping of the process before each copy. It cannot tell V8's mark from one another library put on memory of its own for a reason, so such memory is copied as well.

### The addon

`pnpm build:native` compiles it with `cargo`, for the platform of the Node that runs it, into `build/fork.<platform>-<arch>[-gnu|-musl].node`. The tool looks for that file first and for a package named after the platform second.

Nothing is published yet. The intended shape is one package per platform (`npm/`, in the layout `napi create-npm-dirs` makes), each an optional dependency of the tool so that a package manager installs the one that fits and nobody needs a compiler. Node refuses to run TypeScript sources under `node_modules`, so the package holds JavaScript: `pnpm build` compiles `src/` to `dist/`, and packing does that first. `pnpm test:packed` packs the tool and the addon's package for the platform, installs both next to Vitest into a copy of the fixture project outside the repository, and runs the installed command: every mutant has to come out as from the sources, with runs made in copies, which only happens when the addon is found through its package. The workflow below does that on every platform. By hand the packed tool was also run on immer (Vitest 3) and ufo (Vitest 4), and agreed with the ground truth on every mutant: installed, the code that runs inside the workers is loaded by Node itself and not through Vite, as it is from the sources. One thing is missing: the root package does not list the six as optional dependencies, which it cannot before they are on the registry; that is for the step that publishes to write in.

`.github/workflows/native.yml` builds and tests all six on every push: macOS on arm64 and x64, Linux with glibc and with musl on both. On each, the tests of this repository pass with copies on, and every verdict on the fixture project is checked against the project's own suite (see [Checking the verdicts](benchmark.md#checking-the-verdicts)).

On Windows there is no addon and every run is made in a worker started for it. The same workflow runs the tests and the checks of the fixtures on a `windows-2025` runner with Node 24; one test of the fixture, which sends its own process a signal, is left out there. ufo `all` was run there once by hand, on 9 October 2026, and its 746 verdicts agreed with the stored ground truth. No other scope has been run on Windows, `--changed` has not, and nothing has been timed there. Before it was first run there the tool reported every mutant as not covered and ended as if all were well: it compared the path of its runner with the one Vitest hands back, letter for letter, and Vitest writes the separators its own way.

## Around that

15. **Results carry over between runs, on request.** With `--incremental`, a test file's results are reused when every module it loaded last time, its snapshot file, the lock files, the config and the limits are unchanged, and no mutant is new to it. Only the other test files run again. What a test reads from disk in other ways is not tracked, which is why this is opt-in. Which test detected each mutant is remembered separately, under the mutant's file, kind and the text of its line, and survives whatever else changes: on the next run that test gets the mutant first. That only changes the order, so it cannot change a verdict.
15. **Workers are replaced before they use too much memory.** Thousands of repeats accumulate whatever a test leaks, and before Vitest 5 the mock registry keeps every `vi.fn()` alive. Mocks created during an attempt are held weakly, which `vi.clearAllMocks()` and its kind still reach whichever way the Vitest version goes through the registry (see [Deciding](#deciding)), and a worker whose live heap or resident size passes a limit hands its work over to another.
16. **The mutated source is what Vitest loads, not a rewrite of what it loaded.** Other plugins change the source before a transform sees it, `import.meta.env` for one, and the places the mutants were put no longer line up; a transform that then leaves the file alone makes every mutant in it look unreached.
17. **Vitest is kept from giving up.** An error Vitest cannot serialise, an assertion holding a revoked proxy for one, makes it abandon the test, and before Vitest 4 the rest of the suite with it; errors thrown under a mutant are reduced to their message first, and what still gets through is detected and left to a fresh worker. The pool of Vitest 3 answers a worker that ended itself by sending it a teardown message, takes the failed send for another error of that worker, and loops on that for the rest of the run while every other worker waits for it; sends to a worker that is gone are dropped.

## Tuning

| Option | Default | Effect |
|---|---|---|
| `--max-workers` | the number of processors | More than that and tests that wait on the clock fail on a machine that is behind; a third more gave wrong verdicts on hosted CI runners. |
| `--recycle-heap-mb` | half the machine's memory divided by the workers, at most 1,536 | A worker hands over once its live heap passes this, or its resident size passes 1.5 times this. Lower uses less memory and costs more restarts. |
| `--changed <ref>` | | Only mutants whose code lies entirely on lines changed since `ref`. |
| `--confirm <n>` | every test file that reaches the mutant | A mutant that has passed the `n` test files nearest to it is run against no more, and is reported as Unconfirmed where more reach it. |
| `--led` | off | A mutant a test failed with while trying it is not run whole, and is reported as Led. A failure of a run next to others that no lead vouches for gets neither the tries made with the file to itself nor a run made with nothing else running, and the mutant is reported as Unconfirmed with the file named. A try that ran out of the time Vitest gives the test is no lead to take at its word, having no run without the mutant after it: the mutant is run whole, and reported as Unconfirmed with the file named where that run failed next to others. |

`--confirm` gives up part of the answer for time on the mutants that survive. A mutant no test detects is the costly kind: it has to pass every test file whose tests reach it, and in a project whose tests all go through the same code that is every file for most mutants. The test files are taken nearest first: two by how many of the source file's mutants their tests reach, two by how large a part those are of everything their tests reach, then the rest by the first measure. With a limit the run stops there, and where two files are as near as each other the path decides and not how long they took, so that which mutants are left open does not depend on how long anything took; it does depend on what the tests were seen to reach, which differs between runs where a test reaches code in some runs only. A file in which a test failed or stopped answering while trying the mutant is run whatever the limit. Nothing is concluded from the runs not made: such a mutant is Unconfirmed with the number of files it passed and the number left, never Survived, and the score counts it as survived, so that the score with the option is at most the score without.

What `--confirm 4` leaves out, against a run without it of the same scope:

|---|---|---|---|---|
| jotai `vanilla` | 3,412 | 1,587 | 72 | 0 |
| xstate `core` | 4,744 | 1,619 | 90 | 0 |
| pinia `pinia` | 1,482 | 858 | 60 | 0 |
| Effect `data` | 7,727 | 2,559 | 28 | 2 |

In seconds, on the Linux runners with both runs in one job and so on one machine, one run each: Effect `data` 1,526 without the limit and 731 with it, xstate `core` 449 and 304, jotai `vanilla` 448 and 318, pinia 51 and 37, query `core` 458 and 437, immer 544 and 525. h3 `utils` took 1,442 and 827, of which less is the option's than it looks: the run without the limit took 40 rounds where other runs of the same code took 16 to 26.

Every other mutant has the status of the run without the limit, but for one of h3 whose test passes or fails with it by chance (two runs of six fail, written into the source) and two there that a test reaches in some runs only. Where few test files reach a mutant the option saves nothing, and it never saves anything on a mutant that is detected.

A run without the option says what it would have left out for 1, 2, 4 and 8 files, going by where on each mutant's list of nearest files its runs fell: the share of the time spent on whole-file runs made past that place, and how many mutants a file past it detected. The second is an upper bound, as a nearer file that was not run might have detected the mutant too. On jotai `vanilla` it gave 47% and at most one mutant for `--confirm 4`, and the run with the option spent 56% less on whole-file runs and left no detected mutant open.

`--led` gives up part of the answer on the mutants that are detected. Nearly every detected mutant was first failed by a test while trying it in a worker, and what is then left is a run of the file whose test it is, made only to confirm what that test showed: cheap for each mutant, but there are thousands. With the option such a mutant is left at that and reported as Led, with the tests that failed with it and whether one of them did so with no other run of its file under way. A lead whose test failed again without the mutant, or whose test fails by chance, is no Led: those mutants are run as without the option, and so is every mutant no test failed with, so that Survived means what it does without it. The score counts a led mutant as survived, which on the four scopes below left it between 0.2% and 10%, and the run says what it would be at most with every led mutant detected. The option is for a list of what survives. Which mutants end led and which killed depends on whether a run of the file was already planned when the lead came in, so it differs between runs; which survive does not. A lead that comes to count only later, a test's one run in a copy once a copy with no mutant has passed it, leads too: in rea's `ExecFileOutput.ts`, whose tests sleep for seconds, five such mutants had gone on to runs of the whole file, and the run went from 1,404 s to 1,030 s with every survivor as before. What settles a failure that no lead vouches for is left out too, the tries of a test with its file to itself, one after another, and the run made with nothing else running: such a mutant is reported as Unconfirmed with the file named. On rea's `ExecFileOutput.ts` that took the run from 905 s to 634 s, and every mutant left so was one the run without the option detects; on hono `router` two of them the run without the option has as survived, both having failed in the file whose test of the time it logged fails by chance. Nor do the tries wait on one another: every test tries all it reaches in one round, a mutant one test kills being passed over by the others as they come to it, and a file gets twice the workers its share of the tries would give it, since a worker cannot move to another file and the tries of a file whose tests sleep take far longer than its unmutated runs say. rea's `ReverseEngineeringService.ts` went from 188 s to 149 s and 154 s, under StrykerJS's 211 s on the same machine, and `ExecFileOutput.ts` from 634 s to 579 s and 623 s.

| Scope | Without | With `--led` | Led | Of those, the suite passes with |
|---|---|---|---|---|
| jotai `vanilla` | 81 s | 51 s | 838 | 0 |
| hono `router` | 45 s | 40 s | 955 | 0 |
| solid `reactive` | 688 s | 508 s | 866 | 1 |
| h3 `utils` | 566 s | 304 s | 3,213 | 0 |

One run each, one after the other on a 12-core machine. The score with every led mutant counted as detected was within half a point of the score without the option on all four. Two of h3's led mutants were reported as survived without the option: mutants of `useSession` that make a test a matter of chance, which the suite fails with written in ([Limits](limits.md), tests that fail now and then). A wrong Led is a lead that a run of the whole file does not repeat, of the kinds listed under Deciding: the test fails because of what the mutant, switched on in the middle of a worker's life, did to it, or by chance.

Things that turned out to matter, each measured:

- **The pool of Vitest 3 only starts a worker while it has fewer workers than queued files**, so with a few long runs in flight the last, short ones waited although most of the allowed workers were idle. Asking it to keep the full number alive took excalidraw `math` from about 189 s to about 173 s at the time.
- **The same pool loops on a worker that ended itself** (see step 13). On immer, where workers are replaced often, that alone was the difference between 180 s and 55 s.
- **In a round long enough to give every worker several runs, the runs are shuffled** instead of started longest first: a fixed order gives the tests of the last files their turn only when every other test has already tried the same mutants.
- **Node's compile cache is turned on for the workers.** Where a whole-file run is mostly the start of a worker, it took jotai from 171 s to 151 s and immer from 90 s to 81 s.
- **Whole-file runs are not held back where they rarely fail.** They start a few files at a time per mutant so that a detection spares the rest, but every such step ends on its slowest run. Once fifty of them have run with under one in twenty failing, the rest go at once, longest first. With that, one worker per file for the mutant-free pass, no more than two extra workers for a file whose workers had to be replaced, and the limit on trying mutants in passing checked per mutant rather than per test, immer went from about 95 s to 72 s, hono `utils` from 107 s to 83 s and excalidraw `pr` from about 147 s to 127 s.
- **A worker that blocks is stopped after what a run may take, not five times that.** immer has a mutant that never returns from an iterator; waiting for it took 90 s of a run that now takes that long in total.

## Whether the switches change the code they sit in

Everything above assumes that code with no mutant on behaves like the code it was made from. `bench/conformance.ts` checks that against [test262](https://github.com/tc39/test262): each test that runs as a strict-mode script is run as it is and instrumented, and the two must end the same way.

```sh
git clone --depth 1 https://github.com/tc39/test262 bench/.work/test262
node bench/conformance.ts bench/.work/test262
```

Of 36,071 tests that got at least one mutant, 36,045 end the same. The 26 that do not:

- 20 compare what `Function.prototype.toString` returns, which is the instrumented text (see [Limits](limits.md)).
- 6 run into the check's two-second limit; without it they pass.

One more takes the process down and is skipped. The first run of this check had 95 differences, and five kinds of them were defects: internal lists that went through accessors a test had put on `Array.prototype`, arrow functions in class fields losing their name, `(a?.b)()` and method calls on `Object` or `Math` losing their receiver, and functions holding `var x` next to `function x() {}` no longer parsing.

With `CONFORMANCE_MUTANTS=3` the check also turns on up to three mutants per test, taken from the code the test runs, and compares each with the test's text with the mutant written into it. Over `test/language`, 16,174 tests with a mutant, that found one kind of mutant a switch cannot stand in for: a block emptied in the source takes its `var` declarations with it, so code after it that reads one fails for the name not existing, while a switch only skips the block and the declarations stay. In 7 of 21 such tests the written mutant failed and the switched one passed. Blocks that declare a `var` are no longer emptied, other than function bodies, which keep their declarations to themselves. The differences that remain are messages: the engine words its own errors after the text of the code, and tests print functions.
