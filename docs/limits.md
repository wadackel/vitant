# Limits

What vitant cannot judge, or judges differently from the suite, and why.

- **`Function.prototype.toString` returns the instrumented text.** A test that compares a function's source, or a library that parses it, sees the switches, and in any module of the project that reads a binding a mutant can change only by being read ([Deciding](design.md#deciding)), the mark of that read at the start of the function. So does a test that expects the exact wording of an error the engine raises, `x.y is not a function` for one: the wording follows the text of the code.
- **A walk from `globalThis` meets only what was in place before the test file loaded.** What the instrumented code and the runner keep, the switches, the marks of what ran and what the hook observer and the channel watch share with the runner, is in bindings of the global scope (`__vitant__`, `__vitant_hook`, `__vitant_unanswered`) that no property of `globalThis` leads to. A test that compares everything reachable from `globalThis` before and after its code runs, as fast-check's do after every property with `@fast-check/poisoning`, finds nothing changed there that the suite would not change (`sign.test.ts` of `fixtures/basic`). What it does reach of the tool's is put in place before the project's code runs and stays as it is: in every worker a listener of the process's `exit` event, in workers that are copied, the functions in place of `Date`, `performance.now`, `process.hrtime` and `process.uptime`, `process._send` and the listener of the channel watch, and in a copy made before the file loads the guard on `process.exit` ([What a worker is given](design.md#what-a-worker-is-given)). Such a test tells those from Node's by their source alone (the clocks of a copy, below). Two things change later in a copy made while the file loads or once it has: `process.pid`, which is the copy's own from then on, as under copies below, and the `_idleStart` and `_idleTimeout` of the timers set while the file loaded, which the copy puts off, as under the clocks of a copy below; a test that kept them from the time the file loaded and compares them in a later test sees them change where the suite does not. Under `__vitest_worker__`, which Vitest changes itself as tests run and fast-check leaves out, the tool puts a proxy in place of `rpc` before the file loads and a function that writes nothing in place of the snapshot environment's `saveSnapshotFile` at the end of every suite.
- **A block that declares a `var` is not emptied.** See [Whether the switches change the code they sit in](design.md#whether-the-switches-change-the-code-they-sit-in); StrykerJS does make that mutant.
- **A lock left by a worker that was stopped is cleared by its process id.** Where the system gives that id to a new process before the next look, a tenth of a second later, the lock stays and the run does not end. No verdict comes of it. It has not been seen; Windows hands ids out again sooner than the others.
- **Copies of a worker need `fork()`** and the addon for the platform; elsewhere the tool starts a worker per run. A copy shares what the worker had open when it was made: its random number seed, its standard streams, its channel to the main process. Code that kept the process id while the file loaded, or in a test before the one a copy was made at (see [Making such a process cheap](design.md#making-such-a-process-cheap)), has the worker's: a test that compares it with `process.pid` sees two. Where a copy is stopped in the middle of a message to the main process, the rest of the worker's run on that channel is lost and the run does not end; a copy sends none of the long ones. On macOS a copy that blocks outlives a worker that dies before it; on Linux the kernel stops it. Workers run V8 single-threaded when they are to be copied, which makes the tests themselves somewhat slower and has a full collection of garbage, which otherwise marks beside the program, be through at another point of it; a test whose outcome depends on that point is judged as at the point it meets here ([What a worker is given](design.md#what-a-worker-is-given)). A copy is made only where no thread has started since the file began to load, libuv's pool aside ([Making such a process cheap](design.md#making-such-a-process-cheap), item 12); the threads that were there by then, Node's own and any that the test environment's native modules started, are in no copy either, and a run that needs one waits for it in vain.
- **Tests run in processes, whatever pool the project chose.** The workers are Vitest's `forks`, which copies need, where a project can choose `threads` or `vmThreads`. A test that tells the two apart sees a process: with `pool: 'threads'`, a test asserting that `isMainThread` of `node:worker_threads` is false passes the suite and fails here with no mutant on, and is left out of every run, so that the mutants it alone reaches are reported as not covered, and those in the sources its file loads as Unconfirmed with the test named. Before Vitest 4 the workers of every project are one pool, which takes one list of arguments: where a project's config has the projects the tool runs in pools its `poolOptions` give different `execArgv`, the workers get the list of the pool the first of them runs in, and a test that needs the list of another fails with no mutant on and is left out. The pools a file is sent to by `poolMatchGlobs` count with the rest. The summary at the end of a run names the pools whose lists were not given, and the report has them under `leftOut.poolArgv`. A project that extends a file and names no pool runs in the pool of that file, which the tool does not read: it is named by that file instead. From Vitest 4, where copies are made, an argument of the project's own that is one the copied workers get, `--single-threaded`, is taken off the workers of the first round. A runner the project names (`test.runner`) is not run either: the tool's runner is Vitest's own with what it adds.
- **Type tests are not run.** Vitest can run a type checker next to the tests, and a mutant that only breaks types fails such a run with every test passing. Type checking is switched off here, as StrykerJS does without its checker plugin. Where the project's config has it on, the report says so. h3 has: of its 670 surviving mutants 86 fail the suite, and all 86 pass it with the type check off (`--typecheck.enabled=false`); an optional chain made unconditional is one. The type check does not give the same answer every time: five mutants checked twice failed it once and passed it once.
- **A test file is the unit.** A whole-file run reproduces what a mutant does within one file's run. What tests in one file leave for another file, a `globalSetup`, a server or a file on disk, is outside it. A `globalSetup` runs in the main process with no mutant on, so a mutant in code only it reaches is reported as covered by no test, though the suite with the mutant written in runs that code mutated. Nor is anything done about two different test files that get in each other's way, over a port or a path both use. A plain run puts files side by side too, so a suite that passes stands the pairs Vitest happens to make; here there are many more runs of other files next to any one. Three ways to a wrong verdict are left by that, none of them seen in the scopes checked against ground truth: a test fails on another file's hold of a port while it tries a mutant, passes without the mutant once the port is free, and fails the same way in the run of its file, and the mutant counts as killed; another file leaves something behind that is not tracked by git, and the run made with nothing else running fails on it as well; a run of another file writes what the mutant should have kept a test from finding, and the file passes. Recording what each run writes and listens on was considered and left: it would change the functions the tests call, would not see what a child process or a native module does, and a path two files share says nothing about harm. What tells is the check that exists: `bench/truth.ts` on a sample of killed and surviving mutants, one run at a time.
- **Tests that are retried, repeated or expected to fail are not asked to try mutants.** A test with `retry` or `repeats` set, or declared with `test.fails`, runs as the project has it, and so does what is left of a test that skips itself; the mutants they reach are settled by whole-file runs alone, as are those in code only `beforeAll`, `afterAll` or a shared fixture reaches.
- **One test file runs in many processes at once,** which a plain run never does. Tests that listen on a port, or write files next to themselves, then get in each other's way. A file in which a run failed and another run with the same mutant passed is taken to be such a file: from then on nothing of it runs in two processes at once, and what ran side by side until then is run again, the runs that passed as well, since a run can pass on what another wrote. Where a test that failed in such a run reaches the mutant, the mutant is left Unconfirmed when its file then passes: the failure may have been the other runs or the mutant making the test a matter of chance, and nothing tells the two apart. Which mutants that befalls depends on which runs met, so two runs of the tool name different ones: on tsdown, whose tests build into a directory named after the test and empty it first, two plain runs of `tests/e2e.test.ts` at once fail each other with no mutant on, and five runs of `src/features/entry.ts` left two to six of its 137 mutants Unconfirmed, six different ones in all, every other verdict the same; the suite passes with each of the six written into the source. Only a test that fails and passes with nothing else of the file under way is left out as failing by chance. A file that nothing but such tests gave away goes back to running side by side: a test that sleeps a second and checks the clock gets in nobody's way, and its file, run one process at a time, took a second a run (hono `utils`). A file whose runs fail each other every time shows no pass to go by, and every mutant in it looks killed. So where a mutant failed without a lead, two runs of the file are started at one moment with no mutant on, and if either fails the file is treated the same way. And a lead counts for what it is only when one worker had the file to itself, as in the first round, in a later round that gives the file one worker, or in a file that runs one process at a time: tests trying mutants side by side can fail each other into a lead, and the run of the file that is to check it can fail the same way. A lead from a later round names the file to run and no more, which costs a second run for those mutants: 7% of the time on jotai, 10% on immer, 20% on query. What is left: two runs started together need not meet at the port or the lock they would fight over, and a file with nothing but passing runs and leads of the first round is never asked. The report names the files run one at a time; the output names the first ten of them, and up to three tests behind each mutant left Unconfirmed this way. All of this is per test file. Two test files that share a port or a fixture are run side by side by a plain run as well, but not hundreds of times over, and nothing here sees them fail each other or keeps them apart. That comes too late where the damage stays. vite has tests that rewrite a fixture under version control and put it back when the test ends; two runs at once read each other's half-written state and leave the file broken for every run after them, the tool's own and the project's. After a run on vite two such fixtures differ from the repository. tsdown reaches a tracked file another way. Each of its tests builds into a directory under `tests/temp` named after the test, emptied first, and tsdown looks upward from the fixture for the package it builds: where two runs of one test meet, one empties the other's directory, its `package.json` included, before the build, and tsdown takes the repository's own `package.json` for the fixture's and writes the fixture's `exports` into it. With that file made read-only for one run of the `features` scope, six writes to it failed, from three tests, in two files: five were made while another run of the same test had begun within 40 ms, three of them in workers trying mutants of `shims.ts`, `deps.ts`, and `shebang.ts`, `hooks.ts` and `output.ts`, and two in tests that judged none, and the sixth in a run of the whole file with a mutant of `cjs.ts`, while three other runs of that file were under way. Of three runs of the scope with the file left writable, one on a 12-core Apple M6 and two on hosted runners, two left it rewritten; in a hosted run over all of `src`, 4,031 mutants, a test of `packages/exe`, whose sources import `tsdown/internal`, then failed to load, and 2,180 mutants were left pending. The target and its ground truth stay in `bench/`, and the benchmark workflow does not run it. A project whose tests change files they share is not one this tool can judge. Finding the test files that write, running them one at a time and putting the files back after each run was thought through and left: a mutant can make a test write elsewhere or skip putting a file back, what is not under version control is not seen, and where the files are found changed with nobody to name for it the only sound thing left is to stop. vite's `build.spec.ts`, which does this, is one of 57 test files there, and none of the other eighteen targets has one. What it does is say so, and end with a failing exit code: files under version control that do not hold what they held before the run are named in the report, also those someone was already changing, and on vite, and on tsdown where the file was rewritten, that is how the run ends. It is also said at the end of the round in which it first happens. A mutant can also make a project's tests destroy something every later run needs that is not under version control. Shopify CLI's `archiver.ts` makes the path of a temp file as `join(tmpdir(), `${randomUUID()}.tar`)` and removes it when it is done; with the name dropped, the test removes the temp directory itself, as much of it as the user may. On a hosted macOS runner, where the user owns that directory and all that is in it, it went entirely: every later run of another mutant that made a temp directory, or resolved the temp directory as its file loaded, failed, the tool gave up on two test files, and 610 of 1,796 mutants were left pending. The suite with that mutant written in fails and stops there; the tool goes on to other mutants in what is left. Putting the directory back, and a temp directory for each worker, are under [Measured and dropped](decisions.md). The Shopify scope leaves `archiver.ts` out. What the tool keeps out of such a mutant's reach is what its own process serves: Vitest, from version 4, hands its workers each module as a file it writes once in a directory under the temp directory, and when the removal took those files as well, on macOS, every worker that loaded a file after it failed outside its tests (ENOENT). Vitest's directory is made in the session, under the project's `node_modules`, instead (`sweep.ts` of `fixtures/basic`). A run that needs the temp directory itself to exist is not kept from such a mutant: a test that fails in its body for want of it fails its runs with every mutant tried after, the runs that confirm them included, so a mutant the suite passes with can be reported Killed. Where the temp directory the workers were given is gone at the end of a round, or of the run, the run says so and ends with a failing exit code, as for files under version control. What a test removes from inside the directory, or a directory removed and made again, is not seen. Nor is one more thing the suite does with it done here: in a plain run on macOS the files Vitest loads after the removal fail outside their tests, so the suite fails with the mutant whatever its tests say, where here it is judged by its tests alone, and one that empties the temp directory and passes them is Survived.
- **Runs that confirm a failure go beside other files' runs, unless `--strict`.** A failure of a whole-file run that no lead vouches for is confirmed by a run of the file with no other run of it under way, by default next to other files' runs. A test that fails on a busy machine can then fail twice for a mutant it has nothing to do with, and two test files that share a port or a path, which the suite may never run together, can fail each other: either is a mutant reported as killed that the suite passes with. A file whose runs have been seen to fail each other waits for the machine to itself. `--strict` makes every such run alone on the machine. Both failures have to be of the same test, so two tests that each fail once by chance, one next to other runs and one with nothing else running, no longer make a kill, as they did for a mutant of excalidraw's `textWysiwyg.tsx` that the suite passes with; such a mutant gets one more run with nothing else running and is left Unconfirmed where no test fails twice. What remains is one test that fails twice by chance for a mutant it has nothing to do with, once of the two with nothing else running, which `--strict` makes rarer and nothing here rules out.
- **Tests that fail now and then.** A test found to fail with no mutant on is left out of every run that follows, and a mutant it reaches that passes everything else is reported as Unconfirmed with the test named, not as survived: whether that test fails with the mutant cannot be told from a test that fails anyway. Such a test that never passed has no record of what it reaches, and neither what it reached before it failed, which is not recorded, nor what the other tests of its file reach is what it would reach: every mutant in the sources its file loads, and every other its file reached, is then left Unconfirmed. What a file loads is what a run of all its tests loaded, so a source only the test would load past where it fails, as by an import inside it, is not among them, and a file never run through has only what it reached. That can be many: in promptfoo, started as `node` with no `npm_package_version`, which a test of its version route reads, that test failed in every run and left open the 218 mutants that survive in the six sources its file loads; started with the variable, as `npm test` sets it, the test passes and none is left open. In headlamp, while the instrumented code hid a value of `import.meta.env` from the tests, 26 tests failed in every run with no mutant on and nothing was left open for them: four mutants of a condition that runs as a module loads passed 83 runs of files with those tests left out and were reported as survived, and the suite fails with three of them. A test that has passed is held to what it reached while it ran and, as that does not hold a value its file made while loading, to the mutants that changed one: with a test that passed once and then failed, a mutant of such a value that only it detects was reported as survived. On a machine busy with other work two tests of h3 that time out or lose a race there were left out, and three mutants that the suite fails with every time, one test each being all that detects them, had been reported as survived. A mutant can also make a test a matter of chance by itself: with the check for a session already under way taken out of h3's `useSession`, a test that asks for the session three times at once fails in most runs of its file and passes in some, while the suite failed with the mutant fourteen times in fourteen. A run of a file that passes settles the file for the mutant, so such a mutant was reported as survived whenever one did. Where the test that failed reaches the mutant it is now reported as Unconfirmed with the test named; of 672 mutants of h3 that pass every file, 5 had failed a run in such a test. That takes a run of the file that failed. Where the one run made of the file passes, the mutant is reported as survived, as it was once on a CI runner, though the test had failed with it while trying it: that is also what a mutant looks like that comes on in the middle of a worker's life and changes nothing in a run from the start, of which a project has a few (three in pinia), and telling the two apart takes more runs of the file than are made. Written into the source on another machine, that mutant failed the suite 15 runs in 25. A test that fails with no mutant on when its file runs with nothing else running is found by the runs made that way with none ([Deciding](design.md#deciding), item 8), as long as one of them meets it: three such runs miss a test that fails four times in five about one time in a hundred, and one that fails one time in twenty nine times in ten, and that one is caught, if at all, by the rules that follow. A failure counts in the test that had failed with the mutant while trying it, or when it has been seen twice, one of the two with nothing else running. A test that failed and passed with the same mutant, nothing else of its file under way, is left out for every mutant once it has done so with mutants in two places of the code; with one, the mutant may be what made the test a matter of chance, and the test stays in the runs. What it fails then counts only for a mutant it had failed with while trying it and passed without: a test that failed one run of its file and passed another with any mutant has shown that it can, and a mutant that failed nothing else is reported as Unconfirmed with the test named. Whether the two runs were in each other's way or the test waits on the clock cannot be told from them, so this holds whichever it was. A run that a limit ended, that ended with its worker, or that failed with no test to name is treated alike in a file where such a run passed another time or failed with no mutant on, since the limit ends whichever test is running. On 3- and 4-core runners without the copies of workers, a test of hono that checks the time it logged had failed twice for each of two mutants in a router it does not use, once with nothing else running, and tests of h3 that send a body to a port had timed out twice, now one and now another, for nine mutants: all eleven pass the suite. The same tests had failed and passed with other mutants in those runs. By the records of those two runs the rule leaves the eleven unconfirmed, and with them two that the suite fails with and five it was not run with; in thirteen runs on a 12-core machine it changes nothing. What is left: a test that fails by chance even on a quiet machine, twice for one mutant, before it has been seen to pass with any, and the lead that is an artefact of trying a mutant in a worker together with one chance failure of the same test. A test that fails often enough to do so twice in a row before it is caught passing can still kill a mutant it has nothing to do with; the first runs on hosted CI machines, with a third more workers than processors, had one or two such verdicts among 3,000 runs of hono. The number of workers is that of the processors since. With that many workers a 4-core runner still reported one mutant of hono as killed in one run of three, a reversed comparison in a router's sort: three mutants at that place had a lead, and one run of a whole file with a lead was enough then, whichever test failed in it. A lead now only settles a failure of its own test. The report says for every detected mutant which runs and which tests it rests on (`evidence`), and the check against the suite prints that for a verdict it finds wrong; the run in question was made before that, so which test failed is not known. svelte shows the same thing at a larger scale: its two big test files compile a thousand samples to files next to them, copies of a worker that run the same file side by side fail some test now and then, and with the rule as it was 13 of the 69 mutants checked there were reported as killed that the suite passes with. With the rule as it is all 69 agree, 46 of them every mutant reported as survived; sixteen tests are named as failing by chance in that run. What is left of it: a test that fails by chance with probability p can fail while trying a mutant it does not detect, pass without it, and fail again in the run of the file, which is a kill. Each such try that is not followed by a failing run of the file ends the test's part in settling anything, for every mutant, so with K mutants tried in the test that comes to about K·p²·e^(−K·p) a run, at most one in 2K, if the run of a file fails by chance as often as a try does. Next to other runs it fails more often than a try with the file to itself, and what finds the test out comes from the tries alone; so where a test has failed and passed in runs of its file with one and the same mutant, a failure it had given a lead for counts only once it has been seen with nothing else running as well, which in the runs looked at was two mutants of h3 on a macOS runner and none in Effect, excalidraw, shiki or jotai. The same holds where the try ended at the time Vitest gives a test, the failure a busy machine hands out most freely: six to eight mutants a run of h3, one in a run of excalidraw and none in the others. A try the tool's own limits ended (no end to a loop, nothing running and nothing waited for) settles as any other does: 60 to 80 mutants a run of h3 and about 20 of Effect, all as the suite has them. A run made alone for every kill would close the rest and was not built: nearly every kill is settled this way. A mutant that itself makes a test a matter of chance, by bringing what it waits for close to its limit, is killed or not from one run to the next here as it is in the suite. So is one only a test that races reaches: a test of rea reads a 64 MB file against one turn of the event loop and checks the timeout that ends it, and a mutant in the error of that timeout is met only where the read loses. With the mutant written in, the test failed five runs in five on its own and passed one in eighteen six at once; in a run with `--led` the one run of its file passed and the mutant was reported as survived. A test that bounds its own speed fails by chance under the instrumented code, which is slower than the source: vue's "should not lead to exponential perf cost with deeply chained computed" checks that four writes through a thousand layers of computed values take under 30 ms, or 100 under `CI`, and every mutant it reaches that passes everything else is Unconfirmed, 182 in vue's `reactivity` scope.
- **A test file that fails outside its tests with no mutant on is given up on.** A hook or the file itself that fails whatever the mutant, as a `beforeAll` that connects to a database server that is not running does, fails every run of the file and names no test that could be left out. Once a run of the file with no mutant on and nothing else running has failed that way, none of the file's failures counts and no more runs with a mutant are made of it; the run ends naming the file under "gave up on", with every mutant it did not detect left Pending and the exit code 1. The hook is not left out as a failing test is: what the tests under it would do with a mutant, and whether a mutant would let the hook pass, cannot be seen. mikro-orm's suite has such files where its servers are not running: `tests/features/upsert/upsert.test.ts` runs its tests against SQLite, MySQL, PostgreSQL, MSSQL and MongoDB in `describe.each`, and every run of it fails after half a minute spent connecting. A run on `packages/core/src/unit-of-work/ChangeSetComputer.ts` with no filter takes in every test file that loads it, 1,583 of them, that one among them; the suite's own `test:sqlite` selection, `sqlite.test.ts` as the filter, has none such.
- **A timeout is a judgement.** A mutant counts as timed out when one stretch of a whole-file run keeps the process busy for longer than twenty times what the file takes plus fifteen seconds (once it has blocked a worker while a test tried it, four times plus three seconds), a second for a loop that is past fifty times its iterations, or when the run goes for longer than the first of these without moving on, what the file takes being its run from taking it on to its end, loading and hooks included. Moving on is a suite or a test starting or ending, an attempt at a test starting, or the body of a test ending, and the body of a test that has a limit of Vitest's is timed by the clock only while it keeps the event loop from turning, which keeps Vitest's own timer from ending it. With a limit on the run as a whole, thirty tests that each wait a second under a limit of five, in a file that takes a few milliseconds, were a timeout where the suite passes in half a minute. A run that waits for good where Vitest has no limit, while the file loads or in the teardown of a fixture, is a timeout here and never ends in the suite. These budgets include the finite time Vitest grants the current test or hook, and the wait is that much longer too: a mutant that kept a test busy for four seconds where the project gives a test a minute passes the suite, and was reported as a timeout, and so was every mutant of a file whose `beforeAll` took 16 s and whose test took a millisecond. That limit is held by the clock as well as on the processor: the processor time of a process counts the garbage collector's threads too, and a loop that makes objects it keeps for a while used six seconds of it in four by the clock, where the test had five, and was reported as a timeout. Vitest fails a test that returns after its finite limit. A finite hook has its own allowance, including an explicit override: the runner observes that invocation after Vitest installs its deadline, applies that invocation's deadline only while it is active, and checks Vitest's own expiry predicate before interrupting a loop. A hook that catches the interruption is judged by Vitest's resulting task state. The interruption flag alone is not sufficient: a caller can accept a native VM deadline and let the suite pass. Shared supervisors keep the largest hook allowance seen in the whole-file run, which can delay a later stop but prevents a shorter parallel hook from ending a longer one. What remains outside this correction is work with no finite Vitest limit, where the runner's own limits still apply. So is the memory a run may hold: one that comes to hold more than four times what the file's tests left a worker holding without a mutant, and a gigabyte, is stopped, which the suite would not do, and made again with nothing else running, in a worker started for it that may hold three quarters of the machine's memory; only one that goes past that is counted as timed out. A mutant in Effect's `Chunk` makes the suite take 6 GB and fail after 25 s; four such runs side by side had a 16 GB runner out of memory before any limit on time was reached. A process waits for room for what its file's processes were seen to hold before it starts on the file ([Around that](design.md#around-that)), which is a forecast: a mutant that makes a run hold far more than they did meets only the limit above. One that pushed to an array until it could grow no further, past a gigabyte in under a second, and caught the `RangeError`, passes the suite, and had been reported as a timeout when the first limit was the last. A mutant that makes the tests take more than three quarters of the machine's memory and still pass is reported as a timeout where the suite would pass.
- **Hook deadline observation requires a verified Vitest implementation.** The installed timeout wrapper's timer, expiry and settlement structure is checked before it is observed. The structures known are the five Vitest published from 3.0.0 to 5.1.1. On 3.0.0 to 3.0.3 no expression of the wrapper says that a hook still running is past its deadline (3.0.0 and 3.0.1 race the call against a timer; 3.0.2 and 3.0.3 check the clock only once a promise the hook returned settles), so a hook's own deadline never ends a loop in it there, and the limit on the whole run does. A loop that ends within that limit is judged by Vitest as in the suite, and one that never ends would hold the suite forever as well and is a timeout. On 3.0.2 and 3.0.3 a hook that returns no promise has no finite Vitest limit at all: Vitest passes it however late it returns, so one that runs past the limit on the whole run is a timeout here where the suite passes, as with other work that has no finite Vitest limit. An unsupported structure, a changed module or a worker that did not load the observer makes the run fail explicitly. Nothing in the installed Vitest files is rewritten on disk. Disabled hook deadlines retain the existing runner limits; the finite-deadline correction does not establish outcomes for every unbounded hook.
- **Code that only cleanup hooks reach gets no lead.** While tests try mutants one at a time the mutant is switched off before `afterEach` and the hooks like it, so that it cannot keep them from restoring shared state. A mutant in code that only they run is therefore settled by whole-file runs alone, one per test file whose hooks reach it.
- **Hooks outside a test's run have no limit while tests try mutants.** Once a mutant has been on in a worker, a test's run there is held to a limit, with the mutant on or with none, since what an earlier try left can make even a run with no mutant on endless ([Finding where each mutant is likely to be detected](design.md#finding-where-each-mutant-is-likely-to-be-detected), item 7); with no mutant on, a test that has no time limit of its own (`timeout: 0`) is not. Nor is what runs after a run with the mutant off, the `afterEach` hooks, the cleanups `beforeEach` returned, the teardown of fixtures and `onTestFinished`, or the `afterAll` and `beforeAll` hooks of the suites around it: where a try leaves state with which such a hook never ends, nothing ends the worker and the round does not end. That has not been seen.
- **Code that only runs while a module loads** and that no test or hook reaches is normally left unjudged as Static unless `--static` is given. When a test file's coverage cannot be trusted, conservative whole-file checks can also run these mutants in default mode; a confirmed detection is reported as Killed or Timeout. A final Static status means no verdict was established, even if some checks ran. Enabling `--static` is a choice of cost, not a limit: about four in five of such mutants are detected when they are run (217 of 277 over nine targets), but each takes a run of every test file that loads the module, and one that survives goes through them all. Where such code is one mutant in a hundred the run takes no longer; in pinia and jotai, at one in twenty, half as long again; in vue, where 13 survivors are each run with 180 test files, twice as long. Every verdict it adds in ufo, zustand, immer, jotai and hono agrees with the suite. The run says how many mutants were left out.
- **Tests that only reach code when run at the same time.** Tests marked `concurrent` run one after another while what they reach is recorded; code they only get to because another test is in flight is reported as not covered.
- **One run at a time on a project.** Every run uses `node_modules/.vitant/session` under the project's root and clears it as it starts, so a second run begun while one is under way takes the first one's records, plan and state with it, and workers of either may read the other's settings. Nothing stops or reports that. A run of immich's `person.service.ts` that a run of another file was begun beside ended with 119 mutants killed where it kills 373, and exited with 0; the second run reported 47 of the 48 mutants of its file as covered by no test. Until a run refuses to start beside another, runs on one root have to be kept apart by hand, `bench/truth.ts` included, which writes mutants into the sources.
- **`bail` is switched off,** so that one failing run does not call off the others of its round.
- **A copy reads some clocks later than the run it stands for.** A copy made while a file loads or once it has, after other copies, starts from a process that stood still for as long as those took. Timers set while the file loaded are put off by that much, and `Date`, `performance.now`, `process.hrtime` and `process.uptime` leave it out ([Making such a process cheap](design.md#making-such-a-process-cheap)), which takes in what the project reads through them, fake timers installed by its tests included. What reads the time some other way is not: `Intl.DateTimeFormat` formatting the present moment, the times of `performance.mark` and `measure`, the times a file system writes, Vitest's `vi.getRealSystemTime()`, which keeps Node's `Date.now` from before the tool's runtime loads, and the parts of Node that kept the engine's own clock, such as the `Date` header of an HTTP response. Code that notes the time while the file loads through one of those and checks how much has passed since can see more in a copy than in a run of the suite, and fail there. In what else a test can see of them, the clocks in place of Node's are Node's: the constructor of a date and of `Date.prototype`, `instanceof` for dates made by the code, by Node (`fs.statSync().mtime`) and by `structuredClone`, the names, lengths, own properties and their descriptors of `Date`, `Date.prototype` and each function, where each property is kept (`now` on `Performance.prototype`), `Date()` called without `new`, classes that extend `Date`, `Reflect.construct`, the errors for a wrong receiver or argument, and all of that again once fake timers have been put in place and taken away; `fixtures/clock`'s `table.test.ts` holds each against Vitest's main process, which is plain Node. With dates whose constructor was Node's `Date` and not the one in its place, fast-check's date arbitraries, which map a value back to a date only where `value.constructor === Date`, failed three tests in copies with no mutant on and left every survivor of its `check` scope Unconfirmed. Two things cannot be made the same. Each is another function than Node's, which only code that kept Node's from before the tool's runtime loaded can see, and `Function.prototype.toString` gives `function () { [native code] }` for `Date`, `Date.now`, `performance.now`, `process.uptime` and `process.hrtime.bigint`, where Node gives `function Date() { [native code] }`, `function now() { [native code] }`, `function uptime() { [native code] }` and the source of its own `now()` and `hrtimeBigInt()`, and the tool's own source for `process.hrtime`. Another process or thread reads the machine's clock too, which in such a copy is later than the process's by as long as it stood still: a file whose tests start a child process, a worker thread or a thread of a native module has its runs made in copies made before it loads, which never stand still ([Making such a process cheap](design.md#making-such-a-process-cheap)). Not seen are a native module that reads the clock on the thread that calls it or on libuv's pool, as SQLite's `datetime('now')` and isolated-vm's synchronous calls do, a native module's thread that has ended by the end of the file's run, one that a thread of the pool started on Linux, which takes the pool's name, and a test in such a copy that waits, its processor busy, for the process's clock to catch up with the other one, which is stopped as a timeout before anything is seen: a test that compares such a time with one the process reads can fail in a copy where the suite passes.
- **Skipped runs assume deterministic tests.** If a test takes a different path on each run, a mutant judged harmless in the unmutated run might still have changed something.
- **A mutant that changes which tests a file has** is judged by the first failure of the whole-file run, whatever the tests are then.
- **Test files are those that import a mutated file.** Unless `--no-related` is given, the tool runs the test files Vitest relates to the mutated files, as `vitest related` does, which goes by what they import. A test file that meets a mutated module only through a setup file, a `globalSetup` or what another file left behind is not among them, and a mutant only it detects is reported as survived, or covered by no test where nothing else reaches it.
- **A module imported by a path in another case.** On a file system that ignores case, as macOS's does by default, `import { C } from './Consts'` for `consts.ts` loads the file, and Vite serves it under an id of its own that is not the mutated file's: that importer meets the plain code, and the test files that reach the file only that way are not among those Vitest relates to it. A mutant there that only such a file detects is reported as survived.
- **Tests get the environment the tool was started in.** Its workers have the variables of the process that started it, with what the `vitest` command sets (`NODE_ENV`, `TEST`, `VITEST`), the tool's own `VITANT_` ones and `NODE_COMPILE_CACHE` added, and on macOS, where copies are made, `OBJC_DISABLE_INITIALIZE_FORK_SAFETY`. That one turns off the check that ends a process copied without starting a program anew in which a class of the system's frameworks is set up for the first time, so a process a test starts that copies itself that way, and would be ended in the suite, goes on here. The project's config loads in the main process while Vitest is created, and there, from Vitest 4 on, the temp directory is one in the session (see the item on one test file running in many processes at once): a config that hands the tests a path under `os.tmpdir()` hands them one there, and one that loads an environment file without overwriting what is set does not take `TMPDIR`, `TMP` or `TEMP` from it. A value the config sets itself stays. `npx` and a script of the package put the project's `node_modules/.bin` on `PATH` for what they start, and a test that runs a tool of the project by its name finds it only there; a script of the package also sets the `npm_` variables (`npm_package_*`, `npm_lifecycle_event`, `npm_config_user_agent`), and a test of promptfoo's version route that reads `npm_package_version` fails with no mutant on where the tool is started as `node`. lint-staged's integration tests run `oxfmt` that way: with the tool started as `node` and the path of its CLI, 52 of 492 tests failed with no mutant on, as many as fail a `vitest run` started the same way, and the tool left them out of every run and said how many. Start it as the suite is started, from the project's root with `npx vitant` or from a script of the package: `npx` adds the `.bin` of the directory it is started in and of those above it, not that of the directory `--root` names.
- **Tests that read the source from disk.** Mutants live in what Vitest serves, not in the files. A test that reads, builds or lints a source file itself sees the original.
- **Vitest projects.** Projects written inline in the root config are handled: under `test.projects`, and before Vitest 4 under `test.workspace`, the only list Vitest 3.0 and 3.1 have and the one 3.2 reads where `projects` is not given. A project with a config file of its own is not run: the runner reaches it with the rest of the command line, the plugin that puts the mutants into the sources does not, and its tests would pass every mutant without meeting one. The same goes for a project the root config gives as a function or a promise, and for one in a workspace file (`vitest.workspace.ts`, or the file a string `test.workspace` names), whose list the root config does not hold. Of a test file that several projects include only the first project's run counts. Type tests run in the type checker and are not run either. What was left out is in the report with its number of test files, and the summary says that the verdicts are not those of the whole suite. Tests that load a package as it was built, as those of unocss do for the package they sit in, do not reach its sources, and mutants there are reported as covered by no test, which is what they are. Browser mode and the `vmThreads` and `vmForks` pools are not handled; test files that run in a browser are left out and counted in the report. The pool is forced to `forks`, and while tests try mutants one at a time, concurrent tests run one after another.
- **Only JavaScript and TypeScript are mutated:** files ending in `.ts`, `.tsx`, `.js`, `.jsx`, `.mts`, `.cts`, `.mjs` and `.cjs`. A file `--mutate` matches with any other extension is left out, and the run names it with the reason: a Vue (`.vue`) or Svelte (`.svelte`) component among them, whose `<script>` and template get no mutants, though the tests that mount it still run and the modules it imports are mutated. StrykerJS mutates the script blocks of both; why this tool does not is in [decisions](decisions.md). A file that does not parse is left out and named the same way, with the parser's first error.
- **A file the project's own plugins compile otherwise once instrumented is left out.** Vite's plugins transform the instrumented code, not the source, and a compiler among them can give up on it: the React Compiler rejects a hook or component whose code writes to anything outside it while it renders, as every switch and coverage mark does, and leaves it uncompiled. In coder (`241ec8d`), `useDesktopConnection`'s effect depends on a function that only the compiler's memoization keeps the same from one render to the next. Uncompiled, each render ran the effect again, which rendered again, and a test the suite passes at 785 MB ran its worker out of a 4 GB heap with no mutant on, 41,034 mocks alive. Before the first round, every mutated file goes through the plugins of each project that runs mutants, once as its source and once instrumented, in the Vite environment of the project's test environment (`client` for `jsdom` and `happy-dom`, `ssr` otherwise). A file is left out, and named in the output and under `skippedFiles` with the reason, where the two import different sets of modules, as the compiler imports its runtime only into code it compiled (an auto-import or macro plugin that adds imports by what it can read falls under the same rule), where the plugins fail on the instrumented code only, or where they give back the same code for both, as a plugin that caches what it made by file and not by code does. Such a file leaves the exit code as it is, 0 where nothing else fails the run, as every other file left out does; the summary printed at the end of the run gives the number of files left out and names each with its reason. In coder's `src/pages/AgentsPage/{hooks,utils}` that leaves out 17 of 53 files, 2,206 of 5,014 mutants; the check took 2.7 s there. A plugin that treats the two differently without changing what they import is not seen: such a file is mutated, and its verdicts can differ from the suite's. Nor is the check made in the Vite environment the tests run in wherever that is not read from the project's `environment`: a test file that sets its own, Vitest 3's `environmentMatchGlobs` and `testTransformMode`, and a custom environment that runs in `client`; a plugin that makes one thing of a file there and another in `ssr` is not seen there either.
- **No StrykerJS directives.** `// Stryker disable` comments are ignored. The Regex mutator and StrykerJS's statement-removal mutator are missing.
- **Reports.** `--report` writes this tool's own JSON. `--elements` writes what [mutation-testing-elements](https://github.com/stryker-mutator/mutation-testing-elements) displays, as JSON or as a page that loads the viewer from a CDN; it names for a detected mutant the run that failed and not every test that reaches it, and a mutant reported as Static is Ignored there.
